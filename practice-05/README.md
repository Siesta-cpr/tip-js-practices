## Эксперимент с очередями выполнения

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | Заполнить | Заполнить |
| Фактический результат | A, B, C, D, E, F | A, B, C — синхронный код (B выводится внутри `demonstrateAwait` до первого `await`). D и E — микрозадачи: обработчик `then` поставлен в очередь раньше, чем продолжение после `await null`. F — задача таймера, выполняется после опустошения очереди микрозадач. |

После добавления собственного обработчика `Promise.resolve().then(() => log("G: ..."))` сразу после вызова `demonstrateAwait()`:

| Этап | Порядок меток |
|---|---|
| Прогноз до запуска | Заполнить |
| Фактический результат | A, B, C, D, E, G, F |

G регистрируется после того, как в очередь попало продолжение E, поэтому выводится после него, но раньше таймера F.

- Синхронный код: A, B, C.
- Очередь микрозадач: D, E, G.
- Таймер с задержкой `0` ставит задачу в очередь задач; она выполняется только после завершения текущего синхронного кода и всех микрозадач.
- Если удалить обработчик D, выводится A, B, C, E, G, F: исчезает только строка D, относительный порядок остальных не меняется (проверено запуском копии примера без D).

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Готовый учебный API: маршруты задач и категорий, фильтры, ошибки, CORS, отладочные маршруты. Не изменялся. |
| `src/api-client.js` | Общий транспорт: `buildUrl`, `createApiClient` и `requestJson` — GET, `Accept`, тайм-аут и внешний сигнал, проверка `Response`, статуса, `Content-Type`, разбор JSON и единый `ApiError`. О задачах ничего не знает. |
| `src/task-api.js` | Предметный API: допустимые фильтры, маршруты `/tasks`, `/tasks/:id`, `/categories`, проверка схемы ответа, параллельная `loadInitialData`. |
| `src/variant.js` | Данные варианта: `variantNumber = 5`, `variantFilters = { categoryId: 1 }`. |
| `src/main.js` | Контрольный сценарий в терминале: загрузка, таблица задач, ошибка 404. |

`fetchFn` передаётся в `createApiClient`, чтобы модульные проверки подменяли сеть подготовленными `Response` и ошибками. HTTP-ошибки проверяются отдельно от сетевых: `fetch` перехватывается в своём `try`, а `ApiError` вида `http` создаётся уже после получения ответа, поэтому общий `catch` не превращает 404 или 503 в `network`. JSON после разбора проверяется по контракту, потому что синтаксически корректное значение может не соответствовать схеме: например, `data` не массив, повторяющиеся id или неверный `meta.total`.

## Реализация общего клиента

| Требование | Как реализовано | Проверка |
|---|---|---|
| Нормализация `baseUrl` | `new URL(baseUrl)`; допустимы только `http:`/`https:` без query и hash, иначе `TypeError`. Концевые `/` у пути базы и начальные `/` у `path` удаляются, затем части соединяются одним `/` | Проверки клиента 01, 04 |
| Кодирование query-параметров | `url.searchParams.set(name, String(value))`; пропускаются только `undefined`, `null`, `""`, поэтому `false` и `0` сохраняются; объект `query` не изменяется | Проверки клиента 02, 03; интеграция 02, 03 |
| Заголовок `Accept` | `headers: { Accept: "application/json" }`, метод `GET` | Проверка клиента 05 |
| Проверка `response.ok` | Выполняется первой после проверки типа `Response`. Поля `code`, `details`, `message` берутся из `payload.error`, если тело JSON; иначе сообщение `Сервер вернул HTTP <status>.` | Проверки клиента 08, 09, 16 |
| Проверка `Content-Type` | После `ok` и `204`: значение должно содержать `application/json`, иначе `invalid-response` | Проверка клиента 10; интеграция 11 |
| Разбор JSON | `await response.json()` в `try`; `SyntaxError` сохраняется как `cause` у `invalid-response`; для `204` сразу возвращается `null` | Проверки клиента 07, 11; интеграция 10 |
| Ограничение времени | `AbortSignal.timeout(timeoutMs)`; значение по умолчанию задаётся фабрикой и может переопределяться в вызове | Проверка клиента 14; интеграция 12 |
| Внешняя отмена | Внешний сигнал объединяется с тайм-аутом через `AbortSignal.any`. При отказе сначала проверяется внешний сигнал (`aborted`), затем сигнал тайм-аута (`timeout`), иначе — `network` | Проверка клиента 15; интеграция 13 |

## Классификация ошибок

| Сценарий | Ожидаемый `kind` | Фактические поля `ApiError` | Итог |
|---|---|---|---|

| `completed=yes` | `http` | `status: 400`, `code: "INVALID_QUERY"`, `details: null`, «completed должен быть true или false.» | Выполнено |
| `/debug/error` | `http` | `status: 503`, `code: "SERVICE_UNAVAILABLE"`, «Учебная имитация временной недоступности сервиса.» | Выполнено |
| `/debug/invalid-json` | `invalid-response` | «Ответ сервера содержит некорректный JSON.», `cause: SyntaxError: Unexpected end of JSON input` | Выполнено |
| `/debug/text` | `invalid-response` | «Ожидался JSON, получен Content-Type: text/plain; charset=utf-8.» | Выполнено |
| Не запущен API | `network` | `npm run client` при остановленном API: «Тип: network · Не удалось получить ответ сервера.» | Выполнено |
| Задержка больше тайм-аута | `timeout` | `/debug/delay?ms=150`, `timeoutMs: 20`: «Превышено время ожидания ответа.», `cause: TimeoutError` | Выполнено |
| Явный `AbortController.abort()` | `aborted` | `/debug/delay?ms=150`, `timeoutMs: 1000`, `abort()` сразу после вызова: «Запрос отменён.», `cause: AbortError` | Выполнено |

Запрос `completed=yes` выполнен напрямую через `client.requestJson`, потому что `getTasks` отклоняет такой фильтр `TypeError` до запроса.

## Доменный модуль задач

| Вызов | Результат |
|---|---|
| `getTasks()` | 12 задач: `[1, 4, 7, 10, 13, 16, 19, 22, 25, 28, 31, 34]` |
| `getTasks({ completed: false, priority: "high" })` | 3 задачи: `[4, 13, 34]` |
| `getTaskById(25)` | `{ id: 25, title: "Исправить обработку ошибок", completed: true, priority: "high", categoryId: 2 }` |
| `getCategories()` | `1` «Учёба», `2` «Проект», `3` «Организация» |
| `loadInitialData({ categoryId: 1 })` | Объект с ключами `tasks` (`[1, 7, 13]`), `categories` (`[1, 2, 3]`), `meta` (`total: 3`) |

Правила проверки:

- задача: `id` и `categoryId` — положительные безопасные целые; `title` — строка длиной 1–100 после `trim`; `completed` — boolean; `priority` — `low`, `medium` или `high`;
- категория: положительный безопасный целый `id`, `name` — строка длиной 1–100 после `trim`;
- в коллекции id не повторяются, `data` — массив, `meta.total` равен длине `data`;
- фильтры до запроса: только `completed` (boolean), `priority`, `categoryId` (положительное целое), `q` (строка до 100 символов, обрезается `trim`); иначе `TypeError` без запроса.

Ошибка схемы ответа превращается в `ApiError` с `kind: "invalid-response"`.

## Последовательная и параллельная загрузка

Временный эксперимент вне рабочих модулей: два запроса `/debug/delay?ms=150` через `client.requestJson`.

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---:|---:|---:|---|
| Два последовательных `await` | 306.0 | 310.3 | 308.4 | Примерно сумма двух задержек: второй запрос начинается только после ответа на первый |
| `Promise.all` | 155.7 | 155.2 | 155.8 | Примерно одна задержка: оба запроса начаты до общего ожидания и ждут одновременно |

Время сокращается не из-за самого `Promise.all`, а потому, что оба Promise созданы до `await`; `Promise.all` только ожидает уже начатые операции.
