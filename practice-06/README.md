## 1. Цель работы

Связать браузерный интерфейс с учебным HTTP API: отправлять `GET`, `POST`, `PATCH` и `DELETE`, отображать состояния `loading`, `ready`, `empty`, `error`, после каждой мутации повторно загружать список с сервера и не допускать, чтобы устаревший ответ перезаписал новый фильтр.

Результат: задачи и категории загружаются из API, фильтры уходят на сервер как query-параметры, задачи создаются, редактируются, меняют статус и удаляются через API. Проверки Node.js: 70 из 70; браузерные: 13 из 14 (причина одного отказа описана в разделе 5.2).

## 3. Реализация

### 3.1. HTTP-клиент

`src/api-client.js` перенесён из ПР5 (`buildUrl`, проверка конфигурации, тайм-аут, внешний `AbortSignal`, классификация ошибок) и расширен:

- метод нормализуется в верхний регистр; допустимы только `GET`, `POST`, `PATCH`, `DELETE`, иначе `TypeError` до запроса;
- `GET` с `body` отклоняется `TypeError` до запроса;
- к каждому запросу добавляется `Accept: application/json`;
- при наличии `body` выполняется `JSON.stringify` и добавляется `Content-Type: application/json`; без тела этот заголовок не отправляется;
- порядок обработки ответа: проверка, что получен `Response` → `response.ok` (HTTP-ошибка со `status`, `code`, `details`, `url`) → `204` возвращает `null` → проверка `Content-Type` → разбор JSON;
- виды ошибок: `http`, `network`, `invalid-response`, `timeout`, `aborted`. Отказ `fetch` перехватывается в отдельном `try`, поэтому HTTP-ошибка не превращается в сетевую.

Тайм-аут по умолчанию — 3000 мс (`main.js` передаёт `timeoutMs: 3000`).

### 3.2. Доменный API

`src/task-api.js`: чтение перенесено из ПР5 (`getTasks`, `getCategories`, `loadInitialData` с `Promise.all`), добавлены:

| Метод | Запрос | Проверка ответа |
|---|---|---|
| `getTaskById(id, options)` | `GET /tasks/:id` | `data` — корректная задача |
| `createTask(draft, options)` | `POST /tasks`, тело `{ title, priority, categoryId }` | `data` — корректная задача |
| `updateTask(id, changes, options)` | `PATCH /tasks/:id`, тело — переданные поля из `title`, `priority`, `categoryId`, `completed` | `data` — корректная задача |
| `setTaskCompleted(id, completed, options)` | `PATCH /tasks/:id`, тело `{ completed }` | `data` — корректная задача |
| `deleteTask(id, options)` | `DELETE /tasks/:id` | Ответ строго `null` (204), иначе `invalid-response` |
| `resetDemoData(options)` | `POST /debug/reset` без тела | `data.reset === true`, `data.total` — целое |

`options` содержит необязательный `signal`. Перед запросом проверяется положительный целый `id` и фильтры (`completed`, `priority`, `categoryId`, `q`). Схема каждой задачи и категории, уникальность id и `meta.total` коллекции проверяются в `task-api.js` до передачи данных интерфейсу; ошибка схемы — `ApiError` вида `invalid-response`. `id` и `completed` при создании не отправляются: их назначает сервер.

`src/form-validation.js` — `validateTaskDraft(draft, categories)`: название 1–100 символов после `trim`, приоритет из трёх значений, `categoryId` из строки `select` переводится в число и должен присутствовать в загруженных категориях. Пустая строка не превращается в `0`. Возвращает `{ valid, value, errors }`, DOM не читает.

`src/task-view.js` — карточка `li.task-card[data-task-id]` (класс `is-completed` для выполненных) с `.task-title`, `.task-status`, `.task-priority`, `.task-category` и кнопками `toggle`, `edit`, `delete`; все строки выводятся через `textContent`. `renderTaskList` сопоставляет `categoryId` с категорией и заменяет содержимое списка через `replaceChildren`.

### 3.3. Состояния интерфейса

Каждая загрузка начинается с `setListState("loading")` (`aria-busy="true"`). После успешного ответа: категории (при начальной загрузке), карточки, `setTotal(meta.total)`, затем `ready` для непустого списка или `empty` для пустого. При ошибке — `error` с текстом `messageForError` и кнопкой повтора. Отмена (`aborted`) и устаревший результат состояние не меняют и сообщение не показывают.

Пока категории не получены, любая загрузка (в том числе повтор после ошибки) вызывает `loadInitialData`; после этого используется `getTasks` с текущими фильтрами.

### 3.4. Изменение данных

Создание, редактирование, смена статуса, удаление и восстановление набора выполняются одной внутренней функцией `runMutation`: `setMutationPending(true)` → запрос к API → `notify(..., "success")` → повторный `GET /tasks` с текущими фильтрами → `setMutationPending(false)` в `finally`. При ошибке показывается `notify(messageForError(error), "error")`, кнопки разблокируются.

- `submit(draft)`: валидация; при ошибках — `showFormErrors`, запрос не выполняется. В режиме создания вызывается `createTask`, в режиме редактирования (`editingId`) — `updateTask`. После успеха форма возвращается в режим создания.
- `beginEdit(id)` заполняет форму задачей из последнего ответа; `cancelEdit()` возвращает режим создания.
- `toggleTask(id)` отправляет инверсию `completed` текущей задачи.
- `deleteTask(id)` вызывается после подтверждения в `dom-app.js`.
- `resetData()` вызывает `POST /debug/reset` и перезагружает список с текущими фильтрами.

### 3.5. Защита от устаревшего ответа

Перед каждой загрузкой предыдущий `AbortController` отменяется и создаётся новый; его `signal` передаётся в `loadInitialData` или `getTasks`. Дополнительно каждая загрузка получает номер `++loadSequence`. Результат и ошибка применяются, только если номер совпадает с последним. Вторая проверка нужна, если источник данных не отреагировал на сигнал (так сделано в модульной проверке 27: первый ответ приходит после `abort()` и игнорируется). `destroy()` увеличивает номер и отменяет активную загрузку.

## 6. Ответы на контрольные вопросы

1. _Почему `fetch` не отклоняет Promise при ответе 404?_
   Сервер доступен и прислал HTTP-ответ, поэтому для `fetch` запрос выполнен. Promise отклоняется только при сетевой проблеме или отмене; статус 404 нужно проверить через `response.ok` и самому создать ошибку.
2. _Почему ответ 204 нельзя разбирать вызовом `response.json()`?_
   У `204 No Content` нет тела. `response.json()` попытается разобрать пустую строку и завершится ошибкой синтаксиса, поэтому клиент возвращает `null` до проверки `Content-Type` и разбора.
3. _Чем состояние `empty` отличается от `error`?_
   `empty` — успешный ответ без задач, нормальный результат фильтра: показывается сообщение без старых карточек. `error` — запрос не выполнен: показывается причина и кнопка повтора.
4. _Зачем отменять предыдущий запрос при смене фильтров?_
   Ответ на старый фильтр может прийти позже нового и перезаписать выборку. Отмена прекращает ненужный запрос, а проверка номера загрузки гарантирует, что применяется только последний результат.
5. _Почему после мутации список повторно запрашивается у API?_
   Источник истины — сервер: он назначает `id`, проверяет данные и применяет фильтры. Повторный `GET` с текущими фильтрами показывает только подтверждённое сервером состояние, например исчезновение задачи из выборки после смены статуса или категории.

## 7. Вывод

Интерфейс (`dom-app.js`) только читает формы и отображает данные. Контроллер (`app-controller.js`) хранит состояние и координирует сценарии, не обращаясь к `document`. Предметный API (`task-api.js`) знает маршруты и схему, общий клиент (`api-client.js`) — HTTP, JSON, тайм-аут и отмену. Сервер остаётся единственным источником данных: после каждой мутации список запрашивается заново.

Все модули реализованы: 70 проверок Node.js проходят. В браузерном наборе 13 из 14: отказ вызван тем, что условие ожидания в проверке бросает исключение вместо того, чтобы ждать асинхронного появления карточки. Тот же сценарий вручную выполняется корректно.
