## 1. Цель работы

Освоить построение интерфейса из функциональных компонентов и управление данными через состояние React.

Результат: приложение показывает задачи с названиями категорий, создаёт и редактирует задачи с проверкой полей, переключает статус, удаляет после подтверждения, совместно применяет поиск и три фильтра, показывает статистику и число найденных записей. Данные хранятся в памяти страницы: после перезагрузки восстанавливаются исходные 12 задач и начальный фильтр варианта. Это ожидаемое поведение ПР7, так как localStorage и API в работу не входят.

## 3. Компоненты и состояние

### 3.1. Владельцы состояния

| Данные | Где хранятся |
|---|---|
| `tasks`, `filters`, `editingId`, `message` | `App` (`useState`) |
| `draft`, `errors`, `saveError` | `TaskForm` (`useState`) |
| `categories` | импорт из `data.js`, справочник без состояния |

### 3.2. Компоненты

| Компонент | Props | Назначение |
|---|---|---|
| `TaskStats` | `stats` | Всего, выполнено, в работе по полному набору. |
| `TaskFilters` | `filters`, `categories`, `onChange` | Поиск, статус, приоритет, категория и сброс всех фильтров. |
| `TaskList` | `tasks`, `categories`, `totalCount`, `onToggle`, `onEdit`, `onDelete` | «Найдено: N», карточки или пустое состояние. |
| `TaskItem` | `task`, `categoryName`, три обратных вызова | Название, статус, приоритет, категория, кнопки действий. |
| `TaskForm` | `categories`, `initialTask`, `onSave`, `onCancel` | Создание и редактирование с проверкой полей. |

### 3.3. Передача данных

Данные идут сверху вниз через props: `App` → `TaskList` → `TaskItem`. Действия идут снизу вверх через функции: карточка вызывает `onToggle(task.id)`, `onEdit(task.id)` или `onDelete(task.id)`, а `App` меняет общий массив через `setTasks`. Форма вызывает `onSave(value)` с уже проверенными данными. `onSave` возвращает `true`, если изменение принято, и `false`, если редактируемой записи нет; при `false` форма показывает сообщение в `role="alert"` и сохраняет черновик.

### 3.4. Производные данные

На каждом рендере `App` вычисляет:

```js
const visibleTasks = selectTasks(tasks, filters);
const stats = getTaskStats(tasks);
const editingTask = editingId === null ? null : tasks.find(task => task.id === editingId) ?? null;
```

Для них нет отдельных `useState` и `useEffect`, поэтому список, статистика и форма не расходятся после действий. Статистика считается по всему `tasks`, а не по выборке.

### 3.5. Неизменяемые обновления

Все операции в `src/domain/task-service.js` возвращают новый массив и новые объекты: `addTask` через `[...tasks, task]`, `updateTask` и `toggleTask` через `map` с `{ ...task, ... }`, `removeTask` через `filter`. Аргументы не изменяются, исходный набор в `data.js` заморожен. В `App` используется функциональное обновление `setTasks(previous => ...)`. Следующий id вычисляется внутри обновления как максимум полного массива плюс 1, для пустого массива равен 1.

Подтверждение удаления (`window.confirm`) выполняется до `setTasks`, а не внутри функции обновления: в `StrictMode` React может вызвать её повторно, и побочное действие сработало бы дважды. При удалении редактируемой записи `editingId` сбрасывается в `null`.

### 3.6. Ключи и сброс формы

Карточки создаются через `tasks.map(task => <TaskItem key={task.id} ... />)`. Стабильный `id` связывает элемент с его состоянием при удалении и фильтрации; индекс массива здесь сдвигался бы.

Форма подключена с `key={editingId ?? 'new'}`. При смене ключа React создаёт форму заново, и `useState` берёт черновик из новой `initialTask`. Поэтому при переходе от задачи A к задаче B черновик A не переносится. После успешного создания форма сама очищает черновик, после успешного редактирования `App` возвращает `editingId` в `null`.

### 3.7. Форма

Поля управляемые: `value` из `draft`, обновление через `onChange`. У формы `noValidate`, ограничение 100 символов проверяется в `validateTaskDraft`. При отправке вызывается `preventDefault()`, затем `validateTaskDraft`; ошибки всех полей записываются сразу, при ошибке `onSave` не вызывается и ввод сохраняется. Ошибки связаны с полями через `aria-describedby`, неверным полям задаётся `aria-invalid`. Сообщения о результате выводятся в `role="status"`. Значение категории из `select` приходит строкой и преобразуется в число; строка `'2x'` отклоняется.

## 6. Ответы на контрольные вопросы

1. **JSX и строка HTML.** JSX это синтаксис JavaScript, который превращается в вызовы React, а не текст разметки. Внутри `{}` вставляются выражения, атрибуты пишутся как `className`, `htmlFor`, а текст экранируется автоматически.
2. **Props и состояние.** Props приходят от родителя и только читаются. Состояние принадлежит компоненту и меняется через функцию из `useState`, после чего компонент перерисовывается.
3. **Обычная переменная.** Она создаётся заново при каждом вызове компонента, и её изменение не вызывает перерисовку. `useState` сохраняет значение между рендерами и сообщает React об изменении.
4. **Функциональное обновление.** Когда новое значение зависит от предыдущего: `setTasks(previous => toggleTask(previous, id))`. Так используется актуальное значение, даже если обновлений несколько подряд.
5. **Объект внутри копии массива.** Поверхностная копия копирует только ссылки на объекты. Изменение `next[0].completed` меняет тот же объект, что и в старом состоянии, и React может не увидеть изменения. Нужно создавать новый объект: `{ ...task, completed: !task.completed }`.
6. **Стабильный `key`.** Ключ связывает элемент списка с его состоянием между рендерами. При удалении или фильтрации индексы сдвигаются, и состояние перешло бы к другой карточке; `task.id` не меняется.
7. **Выборка и статистика без состояния.** Они полностью вычисляются из `tasks` и `filters`. Отдельное состояние пришлось бы синхронизировать после каждого действия, и оно могло бы разойтись с данными.
8. **Сообщение родителю.** Родитель передаёт функцию через props, дочерний компонент вызывает её: `onDelete(task.id)`.
9. **Управляемое поле.** Его `value` берётся из состояния, а изменения проходят через `onChange`, который обновляет состояние.
10. **`categoryId` из `select`.** Значение HTML-поля всегда строка, а в задаче `categoryId` число. Без преобразования сравнение `'2' === 2` ложно.
11. **Ключ формы.** При смене `key` React удаляет старый экземпляр формы и создаёт новый, поэтому `useState` заново берёт начальное значение из `initialTask`.
12. **Подтверждение вне обновления.** Функция обновления должна быть чистой. В `StrictMode` React может вызвать её дважды, и `confirm` появился бы два раза.
13. **Нет задач или нет совпадений.** `TaskList` получает `totalCount`: при 0 выводится «Список задач пуст.», иначе «Нет задач, подходящих под фильтры.».
14. **`npm test`.** Проверяет чистые функции `task-service.js`: валидацию, фильтры, статистику, операции и отсутствие мутаций. Компоненты, JSX и поведение в браузере не проверяет.
15. **Переход к API в ПР8.** Начальные данные будут загружаться запросом, операции станут асинхронными (`onSave` вернёт Promise), появятся состояния загрузки и ошибки, а id будет назначать сервер.

## 7. Вывод

Интерфейс разделён на компоненты, общее состояние хранится в `App`, данные передаются через props, действия через обратные вызовы. Изменения выполняются чистыми функциями без мутаций, производные данные вычисляются при рендере, форма сбрасывается через `key`. Все 28 тестов, сборка и 18 ручных сценариев прошли. В ПР8 нужно заменить локальный массив на загрузку из API и сделать сохранение асинхронным.
