## 1. Цель работы

Организовать взаимодействие компонентного интерфейса с HTTP API: загрузку при изменении зависимостей, очистку эффекта, операции изменения и повторное получение актуальных данных.

Результат: задачи и категории загружаются с учебного сервера, фильтры уходят в query-параметрах, создание, редактирование, смена статуса и удаление выполняются через API. После каждого подтверждённого изменения выполняется новый GET с текущими фильтрами. Загрузка, пустой ответ и ошибка различаются; при ошибке обновления остаётся последний успешный снимок. Устаревшие ответы игнорируются, двойное нажатие создаёт одну запись, при неуспешной записи черновик сохраняется. Данные живут в памяти процесса API: перезагрузка страницы их не сбрасывает, перезапуск API или «Восстановить набор» возвращают исходные 12 задач.

### 3.1. Эффект загрузки

```js
useEffect(() => {
  let active = true;
  const controller = new AbortController();
  async function load() {
    setStatus('loading');
    setError(null);
    try {
      const result = await api.loadInitialData({ q, completed, priority, categoryId }, { signal: controller.signal });
      if (!active) return;
      setSnapshot(result);
      setStatus('ready');
    } catch (loadError) {
      if (!active || controller.signal.aborted) return;
      setError(loadError);
      setStatus('error');
    }
  }
  void load();
  return () => {
    active = false;
    controller.abort();
  };
}, [api, q, completed, priority, categoryId, revision]);
```

**Зависимости:** `api`, четыре поля фильтра и счётчик `revision`. Поля извлекаются из `filters` до эффекта, поэтому новый объект фильтров с теми же значениями не запускает запрос. `snapshot` и `tasks` в зависимостях нет: это результат загрузки, и его обновление не должно запускать следующий GET.

**Cleanup:** сначала `active = false`, затем `controller.abort()`. Вызывается при смене зависимостей, при размонтировании и в дополнительном цикле `StrictMode`.

`refresh()` увеличивает `revision` через функциональное обновление. Повтор вызывает тот же `loadInitialData`, поэтому после ошибки самой первой загрузки приходят и категории, и задачи.

### 3.2. Служебные ref

- `mountedRef`: признак монтирования. Отдельный эффект с пустыми зависимостями ставит `true` в setup и `false` в cleanup, там же отменяется текущая мутация. Так это работает и в `StrictMode`.
- `mutationRef`: контроллер текущей мутации. Используется как немедленная блокировка.

### 3.3. Отличия от ПР7

Исходный набор больше не импортируется: данные приходят с сервера. Фильтрует сервер, а не `selectTasks`. Id назначает сервер. `onSave` возвращает `Promise<boolean>`. Статистика показывает последнюю полученную выборку (`meta.total`), а не всю базу. Перезагрузка страницы данные не сбрасывает.

## 4. Загрузка и изменения

**Устаревшие ответы.** У каждого запуска эффекта свой `AbortController` и свой `active`. После смены фильтра старый запрос отменяется, а если ответ всё же пришёл, `if (!active) return` не даёт ему записать ни успех, ни ошибку. Проверка нужна и в `catch`, иначе запоздавшая ошибка испортила бы свежий результат. Отмена не показывается пользователю как ошибка.

**Повторная мутация.** Общая функция `mutate(operation)`:

```js
async function mutate(operation) {
  if (!mountedRef.current || mutationRef.current !== null) return false;
  const controller = new AbortController();
  mutationRef.current = controller;
  setPending(true);
  setMutationError(null);
  try {
    await operation(controller.signal);
    if (!mountedRef.current || controller.signal.aborted) return false;
    setRevision(previous => previous + 1);
    return true;
  } catch (operationError) {
    if (!mountedRef.current || controller.signal.aborted) return false;
    setMutationError(operationError);
    return false;
  } finally {
    if (mutationRef.current === controller) mutationRef.current = null;
    if (mountedRef.current) setPending(false);
  }
}
```

Ссылка на контроллер записывается до первого `await`, поэтому второй синхронный вызов сразу получает `false`. Одного `pending` в state недостаточно: оба вызова увидели бы прежнее значение. В `finally` освобождается только свой контроллер. Для мутации свой контроллер, отдельный от загрузки, поэтому смена фильтров отменяет только чтение. Методы `saveTask`, `toggleTask`, `deleteTask`, `resetData` вызывают `mutate` с нужным методом API.

**Ошибка POST и ошибка последующего GET.** Это два независимых результата. Если API подтвердил запись, `mutate` возвращает `true` и увеличивает `revision`; новый GET выполняет эффект. Если GET не удался, он устанавливает `error` и `status: 'error'`, но `mutationError` остаётся `null`, а форма уже очищена. POST автоматически не повторяется.

**Черновик при ошибке.** Если API вернул ошибку или недоступен, `saveTask` возвращает `false`, ошибка сохраняется в `mutationError` и выводится в `role="alert"`. Форма очищается только при `true`, поэтому введённые значения остаются, блокировка снимается.

## 7. Ответы на контрольные вопросы

1. **Эффект, а не тело компонента.** Тело компонента вызывается при каждом рендере и должно быть чистым. Запрос в нём выполнялся бы при каждой перерисовке, а `setState` по ответу вызывал бы новую перерисовку и новый запрос.
2. **Когда вызывается cleanup.** Перед повторным запуском эффекта при смене зависимостей, при размонтировании и в дополнительном цикле `StrictMode` в разработке.
3. **Почему не `async`.** Эффект должен вернуть функцию очистки или ничего. `async`-функция возвращает Promise, и React не смог бы вызвать cleanup.
4. **Зависимости загрузки.** `api`, `q`, `completed`, `priority`, `categoryId`, `revision`: всё, от чего зависит запрос. `snapshot` это результат загрузки; если добавить его, каждый ответ запускал бы новый запрос.
5. **Стабильная ссылка на api.** `api` входит в зависимости. Если бы он создавался в компоненте, ссылка менялась бы каждый рендер и запросы шли бы бесконечно.
6. **Зачем проверять актуальность.** Отмена может не остановить уже полученный ответ или реализацию API, игнорирующую `signal`. Флаг `active` гарантирует, что результат старого эффекта не запишется.
7. **Защита в `catch`.** Ошибка старого запроса тоже может прийти позже нового успеха. Без проверки она поставила бы `status: 'error'` поверх свежих данных.
8. **Цикл StrictMode.** React делает setup → cleanup → setup и проверяет, что cleanup полностью отменяет эффект и повторный запуск даёт тот же результат.
9. **Почему мало `pending` в state.** Обновление state применяется при следующем рендере. Два синхронных вызова оба увидят `pending: false`. Ref меняется сразу.
10. **`true` при ошибке GET.** Сервер подтвердил изменение, оно выполнено. Ошибка GET означает только, что список на экране не обновился.
11. **Повтор POST после тайм-аута.** Клиент не знает, успел ли сервер сохранить запись. Повтор может создать дубликат; сначала нужно обновить список.
12. **Смена фильтров и мутация.** Мутация это действие пользователя, не связанное с фильтром. Её отмена потеряла бы результат или оставила бы неизвестное состояние; поэтому у неё свой контроллер.
13. **Отмена клиентского ожидания.** Сервер может уже выполнить операцию. Отмена прекращает ожидание ответа клиентом, но не откатывает изменение.
14. **`meta.total`.** Это число задач в ответе после серверных фильтров, а не общее количество записей на сервере.
15. **Что не проверяет jsdom.** Реальную сеть и CORS, вид интерфейса, работу с настоящей формой и клавиатурой, Network в DevTools, поведение собранного приложения в preview.

## 8. Вывод

Реализован хук `useTaskData`: загрузка в эффекте с корректными зависимостями, отмена и защита от устаревших ответов, общая функция мутации с немедленной блокировкой через `useRef`, повторный GET после подтверждённого изменения, раздельные ошибки записи и чтения. Пройдены 52 автоматические проверки, сборка, 17 ручных сценариев и вариант 5. При замене учебного API собственным сервером потребуется сохранить тот же HTTP-контракт либо изменить `api-client.js` и `task-api.js`; адрес задаётся через `VITE_API_URL`.
